# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill`. The unit of rigour is the feature, not every sentence: cover every feature file from source and exercise every feature live.

## Outcomes

Pick one, and say which:

- **clean**: every feature got source and live coverage, and nothing is worth shipping. No branch, no PR.
- **changed**: one PR ships proven corrections to the docs, the helpers or the map.
- **blocked**: coverage could not finish, or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Edit only the verification skill's own folder: its `SKILL.md`, `features/` and the scripts it owns. Product code stays as it is during a run: a behaviour the map describes that the app no longer has is either drift in the map (fix the map) or a regression in the product (report it, and leave the map saying what the feature should do).

## Pass

0. **Locate the target.** The project-local skill with Launch and Drive sections and a feature map, `.claude/skills/verify-*/`. With several, ask which; with none, stop and point at `/create-verification-skill`.

1. **Index hygiene.** Read the feature map's README and list its sibling files. Fix missing, extra, duplicate or dead entries.

2. **Source wave.** Read each feature from source, with at most three read-only subagents at a time, each given a few feature files. Each explains how the user-facing feature works from the source, flags likely drift in the map with file citations, and returns one concise recipe for a live check. Subagents never drive the app and never edit files. Return shape: feature summary / source entry points / likely drift or none / one recipe.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; leave clean claims alone. Sweep recent changes (`git log` since the skill's last change) for user-facing surfaces missing from the map, and name a concrete source path before calling one missing.

4. **Live pass.** Required even when the source looks clean. You do all the driving, following the skill's own Launch. Exercise every feature at least once, and hold three rules the whole pass, whatever fails: run Doctor before the first drive and again after any failed or surprising drive, and relaunch when Doctor can't see the failure (a stuck page on a healthy server); evidence captured so far survives every cleanup, checked at its named location; nothing a drive started outlives its use. A Doctor failure caused by drift in the skill is drift: fix it within the edit scope and retry once before calling the pass `blocked`. A feature that can't be reached is `unreachable` only with the concrete missing prerequisite and the route tried; if the map omits that prerequisite, that is drift. Any helper fix gets driven live again before it ships. Final teardown comes after the last drive.

5. **Triage.** A wrong or missing user-POV description is drift in the map: fix it. Working behaviour the helpers can't drive is a gap in the harness: fix it, with the same helpers rule as generation (scripts executable, invocation in the skill body). App behaviour that is actually broken is a product gap: file it as an issue for the maintainer, outside this PR.

6. **Ship or stop.** For `changed`: one PR of proven corrections; re-read every changed file first. For `clean` or `blocked`: no PR; report the outcome and the coverage honestly.

Keep short run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch folder outside the repository; they aren't committed.
