# Testing seams

Where Mylder's tests cut in, what each cut replays or fakes, and what a good test looks like. Fewer seams, placed higher, mean more of the real code runs in every test. There are three seams: two Effect layers inside `src/tracker/`, with a switch for each feed that sets both (`MYLDER_SOURCE` for transit, `MYLDER_AIRCRAFT_SOURCE` for the aircraft), and the SIRI-ET message stream, below the listener's AMQP connection.

Until the Rejseplanen key arrives, production runs on the timetable source (spec #144, ADR 0018), the default, which needs no API: the tracker makes no call on it, and its adapter at the API seam refuses every request. A third adapter answers in Rejseplanen's place wherever every data state must show, in development by choice, in the recordings and in the GitHub Pages demo: the simulated Rejseplanen (spec #29), which builds every answer from the prepared timetable at the runtime's clock.

## The seams

### 1. The API: a recorded `HttpClient` layer

The tracker reaches Rejseplanen through Effect's `HttpClient` service. Live, that is `FetchHttpClient.layer`. In tests it is `RecordedHttpClient.layer(RECORDED_REJSEPLANEN, dir)`, built with `HttpClient.make` through the tracker's one door to Effect's HTTP module, `src/tracker/http.ts`: for each request it reads the service name from the URL path (`journeyPos`, `multiDepartureBoard`, `multiArrivalBoard`, `journeyDetail`, `himsearch`), takes the next file for that service in call order from the recording folder (`journeyPos/0001.json`, `0002.json`, ...), and returns it with `HttpClientResponse.fromWeb`. A file may also describe a failure instead of a 200's body (`{ "status": 503 }`, `{ "status": 401, "body": { "errorCode": "API_AUTH", ... } }`, `{ "status": 429, "headers": { "retry-after": "120" } }`, or `{ "timeout": true }`, which hangs past any client timeout and then answers 504), and a service with no files left repeats its last answer. A departure or arrival board's calls are kept by the stop's platforms they ask for, the `idList` joined by `+`, in a folder of their own (`multiDepartureBoard/8600783/0001.json`, `multiArrivalBoard/8600783/0001.json`), so opening one stop never takes another's board, whatever order riders open them in. A call to a service, or a board for stops, the recording has no files for answers Rejseplanen's `SVC_PARAM` error, so such a stop answers from the timetable. The layer replays any API the same way: it takes the API's description (its folders, the folder a URL calls, the folders it keeps by a key the URL names and that key, its answer to a call with no folder), and Rejseplanen's, `RECORDED_REJSEPLANEN`, lives in its adapter beside its schemas, in `src/tracker/rejseplanen/responses.ts`, and the freezer files each call it tapes by the same rule. An API whose rule names a folder it doesn't list, or a folder that is there but can't be read, fails the replay instead of answering as if it had no calls. Nothing above the HTTP layer is faked: the schemas, the retries, the timeout, the budget, the store, the timetable join and the data-state rules all run as in production. Every source's answers decode with the schemas in `src/tracker/rejseplanen/answers.ts`, whose hand-written contract fixtures sit beside them. The aircraft feed (`docs/aircraft.md`) is the second recorded API, `RECORDED_AIRCRAFT` in `src/tracker/aircraft/source.ts`: one folder, `aircraft/`, for adsb.lol's and adsb.fi's circle queries in call order, so a failure of adsb.lol's is followed by adsb.fi's answer to the same call, failures written the same way, and a 404 for any other call; its answers decode with `src/tracker/aircraft/answers.ts`. The demo's worker, which has no file system, replays the same folder bundled into its script (`bundledFiles`), and starts it again from the first once none are left (`whenDone: 'loop'`), so its planes never stop (`docs/aircraft.md`, "The demo").

A recording is one folder in `recordings/`: the API answers, a `timetable/` folder with prepared files for the same service day and box, `clock.json` with the moment the recording started (`{ "start": "2026-06-16T05:20:00.000Z" }`), `snapshots/` with the tracker's snapshot of each minute, which screen tests use, and `answers/` with the route answers they use beside it: the disruption list of each minute in `answers/disruptions/`, the stop, arrivals and trip answers a plan saves (`answers/stops/`, `answers/arrivals/`, `answers/trips/`), and the aircraft snapshot of each call in `answers/aircraft/` when the recording has an `aircraft/` folder. Recordings are saved from real answers once the key arrives (Record an hour of journeyPos at morning rush (#12)), with the key stripped from any URL. Until then every recording is frozen from the simulation: `npm run recordings` (or `npm run recordings -- <name>`) runs the tracker over each plan in `src/tracker/recording/plans.ts`, a scenario on a fixture timetable (the real `scripts/timetable/fixtures/gtfs` unless the plan names another) for a number of minutes on `TestClock`, opening the stops it names at a minute, on Departures and then Arrivals, so their departure and arrival boards are kept, and rewrites its folder with what the simulation answered and the snapshots and disruption lists the tracker gave. The `weekday` one keeps København Syd St.'s departure and arrival boards, asked at 07:22 while the RE to Næstved stands at its track. The cases a real hour may not show are frozen the same way: `empty` (an empty `journeyPos`), `refused-key`, `spent` (Rejseplanen's quota error; the tracker's own monthly counter running out is a tracker test's to show), `cap` (a 1,000-journey answer, filled with copies under journey numbers no trip has) and `crowded` (six trains standing at København H at once from 07:20 to 07:24, on time, more than the stop panel lists before "Show all"; the real fixture never stands more than one at a stop, so its timetable is prepared from `scripts/timetable/fixtures/gtfs-crowded`, six of the fixture's trains with their times moved by hand, whose version is named by its files' hash so it never shares one with the real fixture's), beside a ten-minute `weekday`. A test replays each recording through the tracker and expects the snapshots and lists it was frozen with, so a change to the tracker's output fails until the recordings are frozen again. Beside the plans, `ON_TIMETABLE` runs the tracker on the timetable source over the real fixture for six minutes from 07:20, the 991 Waiting at Orientkaj St. by the last, and the same script saves its snapshots, disruption lists and the stop, arrivals and trip answers it names in `recordings/timetable-source/` for the screens' tests on that source, and `ENDING_TIMETABLE` runs it for one minute from 07:20 on Tuesday 25 August 2026, the fixture's last week, so the timetable notice shows, into `recordings/timetable-ending/`. Each holds no answers, since the source makes no call, and a `clock.json` with its start, which `MYLDER_TIMETABLE_FROM` runs the timetable source from; a test runs each plan again and expects what was saved. A recording's `aircraft/` folder is never frozen: it is recorded from the feed (the `weekday` one is three minutes of real adsb.lol answers from 26 October 2026), with its own `clock.json` when its answers were recorded on another day, and `npm run recordings` keeps it and saves the aircraft source's snapshot of each of its calls, one every 10 s from that moment, or else the recording's, which a test replays the same way. The cases a real recording doesn't show, such as a PIA-flagged aircraft or a rough position, are hand-made answers in the aircraft route's tests.

### 2. Time: Effect's `Clock`

Every time check in the tracker reads `Clock.currentTimeMillis`, never `Date.now()`. In Vitest, `@effect/vitest`'s `it.effect` provides `TestClock`, so `TestClock.adjust('5 minutes')` moves the tracker's clock without waiting. Under a recording in a production build, the runtime provides a clock that starts at `clock.json`'s moment and advances in real time, so the recorded day is "today" for the timetable and the snapshot's ages are the recorded ones. The offset is taken once per process for each start, so runtimes that start at the same moment, built at different first requests, read the same time; the aircraft's starts at its folder's own `clock.json` when it has one, and the browser keeps the two servers' clocks apart. The browser's clock in Playwright is set with `page.clock.install({ time })` to the same moment.

A run's CPU time comes the same way, from the tracker's `CpuClock` (`src/tracker/report.ts`), never from `process.cpuUsage()` directly: the server provides the process's own, frozen recordings `stoppedCpu` so their snapshots come out the same every time, and a test whatever clock its figure needs.

### 3. The SIRI-ET message stream

SIRI-ET's delays and cancellations (spec #146, ADR 0019) reach Mylder as messages pushed over AMQP to an always-on listener, which no test connects to. Below that connection, each message is a dataset, the moment it was received and its SIRI XML body, and the SIRI-ET reader (`src/siri-et/reader.ts`) takes them one by one and gives the update table at any moment. Tests replay recorded messages into it in order and ask for the table at chosen moments. The listener's own tests (`src/listener/*.test.ts`) replay them into its core and ask its route, as the tracker and strangers would; its loop runs on a fake link in place of the AMQP shell, with Entra ID and the app as a stub `fetch` and Vitest's fake timers as the clock. `recordings/siri-et/` holds 56 real minutes of all four datasets as `messages.jsonl.gz`, one message a line; the reader's tests replay samples of it kept beside them, eight journeys in `src/siri-et/fixtures/sample.jsonl.gz` and bus 118's round trip in `round-trip.jsonl.gz`, each cut by `scripts/siri-et/sample-siri-et.mjs`, since the whole recording, 114 MB of XML, takes seconds to replay; `scripts/siri-et/replay-siri-et.ts` replays the whole for the table's figures. Expected delays are read off the messages by hand, each call's expected time minus its aimed time. A malformed message or a cap is shown by changing a recorded message, never by a hand-written feed.

### The switch: `MYLDER_SOURCE`

One environment variable picks where the tracker's answers come from (`src/tracker/source.ts`), and the tracker builds its runtime from it. It is read at request time, so one `next build` serves CI's Playwright run, previews and production.

| Value                                 | API layer                                                                                             | Clock                                                 | Timetable                    |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------- | ---------------------------- |
| `timetable`, empty or unset           | None called: a layer that refuses every request, logging an error that names the source. The default. | The runtime's: real time, `TestClock` in tests        | The deployed one             |
| `simulated` or `simulated:<scenario>` | The simulated Rejseplanen, under the named scenario (`weekday` when none is named)                    | The runtime's: real time, `TestClock` in tests        | The deployed one             |
| `recording:<folder>`                  | The recorded layer above, replaying the folder                                                        | Starts at `clock.json`'s moment, runs on in real time | The recording's `timetable/` |
| `rejseplanen`                         | `FetchHttpClient.layer`, with the key from its own variable                                           | The runtime's                                         | The deployed one             |

`MYLDER_TIMETABLE_FROM=<folder>`, beside `timetable` and read by no other source, runs it on a saved folder in `recordings/` instead, such as `timetable-ending`: the folder's `timetable/`, served to the browser too, and a clock that starts at its `clock.json`'s moment and runs on in real time, as a recording's does. It is for the verifier, to drive a moment such as the timetable's last week again; production never sets it. On `timetable` the tracker makes no call of any kind: every run builds from the timetable alone, every trip Timetable only, its opened stops and trips answer from the timetable with no on-demand call, and the snapshot names the source `timetable` with position mode `none`, whatever `MYLDER_POSITION_MODE` says. Its keys in the store are its own, as every source's are. It is the default: an unset or empty `MYLDER_SOURCE` reads as `timetable`, so `npm run dev` with nothing set, and a deployment that forgets the variable, show the honest map, never invented realtime. Production runs on it until the key arrives (ADR 0018). The simulation is only ever chosen by name, `MYLDER_SOURCE=simulated`, as the recordings' plans, the demo's worker and the tests that need it do.

The key never picks the source. `rejseplanen` without a key logs the fault and the snapshot's API health reads as a refused key, so a missing key fails visibly instead of quietly showing a simulation. Going live is the key and `MYLDER_SOURCE=rejseplanen` in Production. While the source is not `rejseplanen`, the snapshot names it, and on a simulation, a recording or the timetable every screen says so in a banner. What a rider is told about each source is described once, in `src/domain/source.ts`: whether it asks Rejseplanen, has positions and brings disruption messages, the dictionary keys of its banner, of its name in the About dialog and of About's note on its vehicles, and whose data the transit is credited to. The same file names the modes SIRI-ET's delays never reach, `NOT_IN_SIRI_ET` (the Metro and the light rail), which the tracker's join leaves alone and City pulse's shares with an update read as "—", whatever the source. The domain's rules, the screens and the tracker's run read that description, never the page's source kind; only `src/tracker/source.ts` tells its sources apart, to read the variable, build each one's API and name it in the snapshot. The descriptions are typed over the snapshot's kinds, `SOURCE_KINDS`, so a kind added there fails typecheck until it is described. On the timetable source the banner says every vehicle is placed from its timetable, the About dialog names the timetable as the source, the vehicle and stop panels say their times are the timetable's, City pulse and the Vehicles list name the timetable, the Disruptions screen says messages come with the live connection, and no Paused notice or data card shows.

### The aircraft's switch: `MYLDER_AIRCRAFT_SOURCE`

The aircraft have a switch of their own, independent of `MYLDER_SOURCE` and read the same way (`src/tracker/aircraft/source.ts`): `adsblol` (the default, the real feed), `recording:<folder>` (the recorded layer over the folder's `aircraft/`, on its own `clock.json`'s clock or else the recording's) or `off` (the route answers 404 and the page shows no aircraft). Playwright's recording server sets `recording:weekday`, and every other server it starts `off`, so no test calls adsb.lol.

### The update switch: `MYLDER_UPDATES`

Where the tracker's SIRI-ET updates come from (spec #146, `src/tracker/updates.ts`), independent of `MYLDER_SOURCE` and read the same way, so delays work on the timetable source now and on `rejseplanen` later:

| Value                         | Updates                                                                                                                                            | Clock and timetable                                                                                 |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `off`, empty, unset           | None. The default, so local runs and tests need no listener.                                                                                       | The source's                                                                                        |
| `siri`                        | The listener's update table, fetched once a run from `MYLDER_UPDATES_URL` with `MYLDER_UPDATES_TOKEN` as its bearer token                          | The source's                                                                                        |
| `recording:<folder>`          | The SIRI-ET reader inside the tracker, fed the folder's `messages.jsonl.gz` as the clock reaches each message, its box from the folder's timetable | On the timetable source without `MYLDER_TIMETABLE_FROM`, the folder's `timetable/` and `clock.json` |
| `recording:<folder>/<moment>` | The same, over the same messages                                                                                                                   | The same, but the clock starts at the saved moment's own `<folder>/<moment>/clock.json`             |

Production sets `siri` (#218). Under `simulated` the switch is ignored, since the simulation brings its own updates, and setting both is logged as a warning. `recording:<folder>` is ignored the same way, with a warning, wherever the runtime's clock isn't the folder's: under any source but the timetable, or with `MYLDER_TIMETABLE_FROM` naming another folder, its messages would all be due at once or none would. The snapshot's `updates` block names the kind, the last message's time, whether the feed is fresh, and the trips with an update and the journeys that joined no trip, by mode; it reads `off` with nothing counted when the switch is. Tracker tests replay `recordings/siri-et` with `updates: { kind: 'recording', folder: 'siri-et' }` on that folder's timetable. They prove the `siri` path against the listener's own route: the recording's messages replayed into the listener, its server started on a port of the test's machine, and the tracker fetching from it, which must give the same trips as the reader inside the tracker. Its failures (a timeout, a failed or refused fetch, a stale table, a table of another version) come from a hand-made `HttpClient` in the listener's place, given to `trackerLayer` as `updatesHttp`, as the API's recorded one is given as `http`. A quiet feed is shown both ways (`src/tracker/tracker-quiet-feed.test.ts`): over the recording past its last message, at 09:56:07, and from a hand-made listener fed the recording's messages with some held back, then delivered, as a subscription keeps them. A saved moment is a folder of the recording with a `clock.json` of its own, for the verifier: `recordings/siri-et/quiet/` starts at 09:55:00, so the feed is fresh at launch and quiet 6 minutes in. `npm run recordings` saves the snapshots of 09:21 and 09:22 of the timetable source with those updates into `recordings/siri-et/snapshots/` for screen tests, leaving the folder's messages, timetable and clock as recorded.

The store needs no switch: `SnapshotStore` is in memory whenever no Redis URL is set, which is also how local development runs. Its keys carry the source, so a simulated call counter never shares a key with the real one.

There is no fourth seam: the simulation is an adapter at the API seam, not a seam of its own. Screens are tested with real snapshots (saved from the tracker's output over a recording), the map's loop with real patterns, and nothing in the browser is mocked.

## What each kind of test looks like

Every test asserts external behaviour: what the route returns, what the snapshot says, what a person sees. None asserts that a function was called.

- **Domain** (`src/domain/*.test.ts`): plain Vitest, tables of inputs and expected states. "A trip reported 70 s ago on a 60 s interval is Ageing." "A computed position is never Live." These are the same functions the browser runs, so a table proven here holds on both sides.
- **SIRI-ET reader** (`src/siri-et/*.test.ts`, plain Vitest): replay recorded messages up to a moment and assert on the update table at another. A good one: "IC 50118's message of 09:06:52 carries eight calls; the journey keeps the two the 09:03:41 one set and lists its delays as steps." "Bus 68 leaves the table 10 minutes after it reached Kigkurren at 09:43." "A truncated message is counted as malformed and the next is read."
- **Tracker** (`src/tracker/*.test.ts`, `it.effect`): provide `RecordedHttpClient.layer(RECORDED_REJSEPLANEN, recordingDir('weekday'))` and the in-memory store, then play requests against `Tracker.getSnapshot` with `TestClock.adjust` between them, and assert on the snapshot. A good one: "Two requests 10 s apart make one API call." "A trip in the first answer and absent from the next six, over 6 min, is No signal; one absent for 3 min is Ageing." "When the month's counter runs ahead of the day, `nextDue` stretches to 90 s and `getStopDepartures` answers from the timetable with the snapshot's delay." "Three 503s in a row give `api.health: 'error'` and a 200 with the previous snapshot's trips, still moving on their timelines." "An answer the schema rejects is logged without the key and counts as `error`."
- **Screens** (`src/screens/*.test.tsx`, jsdom, Testing Library): render with a saved snapshot and assert text and roles in English and Danish. "A No signal vehicle's detail says 'No signal since 10:42'." "Metro departures read 'every 3 min'."
- **End to end** (`e2e/*.spec.ts`, Playwright on the production build with `MYLDER_SOURCE=recording:weekday`, every page's clock installed at the recording's moment by `e2e/recording.ts`, and a second server on the same build with `MYLDER_SOURCE` unset, to prove the default source starts: it shows the timetable banner and draws vehicles at the real time, and its snapshot names the timetable source): a few journeys that prove the wiring, not the time rules. The map shows as many vehicles as the recording's snapshot, and as many aircraft as the aircraft snapshot it was served; open one and follow it; a stop's departures; the Disruptions screen; `/da`; the page's notice when its own polls fail (block the route with `page.route`). The 5-minute rules are proven in the tracker tests, where the clock is free. A third server on the recording serves the snapshot route's tests alone: they count its calls, so no other test's stop or vehicle may spend one there. A fourth, on the `crowded` recording, serves the tests that open a stop with more trains standing than its panel lists before "Show all": the side panel's list and "Show all", and a phone's row of six cards with the tabs at the sheet's peek. A fifth, on the simulation by name, serves the tests that need it: the simulated banner, and a page with the aircraft off. A sixth, on the timetable source with `MYLDER_UPDATES=recording:siri-et`, serves the delays' tests: Estimated dots, a delayed bus's card, and the banner and legend that say so.

## Rules

- Recordings carry no key, no personal data and no more than a scenario needs; prefer a hand-made 20-journey recording to a full-city hour where the case allows. A real recording keeps the minutes the tests and the demo use and is cut to a box a little wider than theirs: the `weekday` aircraft to 55.40 to 56.10 N and 12.00 to 12.75 E, plus three aircraft outside it, with every field of each answer kept so the answers stay the shape of the feed's contract.
- A test never reads `Date.now()` on the server side and never sleeps.
- A change to the snapshot schema regenerates the saved snapshots the screen tests use, from the recordings, with one script.
- CI needs no secrets, because no test calls the API.
