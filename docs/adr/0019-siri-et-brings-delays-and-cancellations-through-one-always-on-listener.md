# SIRI-ET from Dataudveksleren brings delays and cancellations, through one always-on listener

Rejseplanen's SIRI-ET datasets on Dataudveksleren, the national access point, bring every trip's expected times and cancellations for Movia (788), DSB (785), the S-tog (801) and Lokaltog (799), from about an hour before each departure (spec #146). They are pushed over AMQP 1.0 to a subscription on Azure Service Bus and can be read no other way, so one small always-on **listener**, outside Vercel, holds the connection. It feeds each message to the SIRI-ET reader (`src/siri-et/`), which merges each journey's calls across messages and keeps the **update table**: the journeys that call inside the box and haven't finished, with their delays as steps, their cancelled calls and whether they are cancelled whole. The listener serves the table over HTTPS, on one route behind a token, and the tracker fetches it on each run and joins each journey to its trip. The listener runs on one Fly.io machine paid from prepaid credits, about $2.20 a month, which the account can't overspend.

This supersedes ADR 0002 where that ADR makes the Rejseplanen API the only realtime source and drops SIRI-ET, as ADR 0018 began. It amends ADR 0001: Mylder gains one always-on process, for this push feed only. The app stays one Next.js app on Vercel, the tracker stays pull-driven, and browsers still poll one cached snapshot. It amends ADR 0012: Mylder is no longer one deployable, since the listener is a second, its own container image (`listener.Dockerfile`), but it is built from a second entry point in the same package, `src/listener/main.ts`, with no workspace.

**Amended on 1 November 2026 (#217): the table travels over HTTPS, not through the store.** Spec #146 had the listener write the table to the server store each minute for the tracker to read back. The table measured about 112 KB gzipped for 1,282 journeys on a quiet Saturday morning (#212, `docs/live-data.md`, "The update table"), four times the 15 to 25 KB the spec budgeted for a weekday peak. Written and read back each minute, it would use nearly all of the store's free transfer, which the tracker's snapshots already use most of. So the listener serves it instead, and the store carries nothing of SIRI-ET's.

**Amended on 1 November 2026 (#215): the delays' credit names no licence.** Every SIRI-ET dataset page on Dataudveksleren says "Licence: None" (#146's access comment), so the credit below no longer puts the delays under CC BY 4.0. About and the map's corner credit name Rejsekort & Rejseplan A/S for the delays and name no licence until Rejseplanen answers which applies; the timetable keeps its CC BY 4.0 credit.

## Considered Options

- **Drain the subscription from the tracker, over AMQP on WebSockets, on each run.** No new host, and the reader would run inside the tracker. Ruled out for now by size: the subscription keeps messages while nobody reads them, so a night with nobody watching leaves hours of Movia's backlog, about 140 MB of XML an hour on a Saturday morning, for the first poll of the morning to read. The reader is one module that runs anywhere, so this can replace the listener without touching the reader or the table.
- **The listener writes its table to the store each minute, and the tracker reads it back.** Spec #146's first choice: no inbound port on the listener. Ruled out by the table's measured size, as above. Writing only the journeys that changed since the last write would cut the writes but not the tracker's whole read each run, and would make the store hold state the listener already holds.
- **Hetzner Cloud.** Was the choice at €4 a month; over €4 since its 2026 price rises, with no hard cap.

## Consequences

- A trip with an update this service day is Estimated, placed from its timetable plus its delay; a cancelled trip is not drawn. SIRI-ET carries no positions, so nothing it brings is Live or Ageing (ADR 0005), and the Metro and light rail have no dataset, so they stay Timetable only (ADR 0006).
- The update table is the contract between the listener and the tracker: versioned and checked with one schema (`src/siri-et/table.ts`) on both sides.
- The listener has one inbound port, with TLS at Fly.io's edge, and serves one route, `GET /table`, only to a request with `MYLDER_UPDATES_TOKEN` as its bearer token: 401 without it, 503 until it has the box's stops and a first table, and nothing else beyond a health check that says "ok" or "starting". It builds the table gzipped at most once a minute and serves it from memory between.
- The tracker's run makes one more call, to the listener, with a 3 s timeout. A failed, slow or refused fetch, or a table built over 10 minutes ago, is no table that run, logged and never failing the run, so a dead or stuck listener never leaves old delays looking fresh: its trips go as `docs/data-states.md` says for a feed that isn't fresh.
- A listener that restarts catches up from the subscription's backlog within seconds; no snapshot is sent on subscribe, so a new subscription starts blank.
- The listener's credentials live only in the host's secrets. No recording holds a credential or a subscription id.
- Rejseplanen's licence for the datasets is unsettled: each dataset page says "None". Mylder credits Rejsekort & Rejseplan A/S for the delays, naming no licence until Rejseplanen says which applies (amended by #215; it first read "under CC BY 4.0 as the Labs guidelines give for its data").
