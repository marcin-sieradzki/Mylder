# Tracker

Runs on the server only. Every module here starts with `import 'server-only'`, so importing one from a client component fails `next build`. Callers go through `index.ts`.

- `http.ts`: the tracker's one door to Effect's `unstable` HTTP module (ADR 0011), knowing no feed: the `HttpClient` service, a client that answers every request itself, the fetch layer, JSON and text answers, the gateway timeout, and a plain GET.
- `rejseplanen/answers.ts`: the Rejseplanen API 2.0 answer schemas every source decodes or encodes with, and their contract fixtures in `rejseplanen/fixtures/`.
- `rejseplanen/responses.ts`: Rejseplanen's answers built on the HTTP door, for every adapter that answers in its place: its error answer (`errorAnswer`), its `SVC_PARAM` refusal (`svcParam`), and how a recording keeps its calls (`RECORDED_REJSEPLANEN`).
- `source.ts`: `MYLDER_SOURCE`, and the `HttpClient` layer each source answers through (`docs/testing-seams.md`). The timetable source is the default, what an unset `MYLDER_SOURCE` reads as, and what production runs until the key arrives (ADR 0018): its layer refuses every request, since that source makes no call and the tracker builds every run from the timetable alone. The simulation is only ever chosen by name, `simulated`.
- `recording/`: the recorded layer, an `HttpClient` adapter that replays a folder in `recordings/` for any API described to it (Rejseplanen's and the aircraft feed's), the clock that starts at the recording's moment, one offset per process, and the plans `npm run recordings` freezes the recordings from, and the timetable source's run it saves beside them, with the aircraft snapshots it saves beside a recording's `aircraft/` folder (`docs/testing-seams.md`).
- `simulation/`: the simulated Rejseplanen (#29), an `HttpClient` adapter that builds answers from the timetable at the runtime's clock, under a scenario.
- `timetable.ts`: the deployed timetable, read once per instance, with service days expanded and pattern paths measured on first use. `testing.ts` holds the fixture timetable the same way for tests.
- `index.ts`: the four plain functions the routes call (`getSnapshot`, `getStopDepartures`, `getTripDetail`, `getDisruptions`); no Effect type leaves the tracker.
- `tracker.ts`: the run (lease, call, build, store); `answers.ts`: the stop and trip answers, pure functions of the timetable and the snapshot, which the on-demand calls fall back to; `on-demand.ts`: the on-demand calls' one-minute cache and their shared limit of ten a minute, behind the budget's on-demand rule; `stop-board.ts`: a stop's answer from its `multiDepartureBoard` call and its arrivals from its `multiArrivalBoard` call, each row joined back to its trip, or from the timetable when no call is made; `trip-detail.ts`: a trip's answer from its `journeyDetail` call, its calls matched onto the timetable's trip, correcting the join's first guess (`corrections.ts` keeps each correction as its own store entry, a journey's latest winning), or from the timetable when no call is made; `runtime.ts` composes its layers once per instance from `MYLDER_SOURCE`, `MYLDER_POSITION_MODE` and `REJSEPLANEN_KEY`.
- `rejseplanen/client.ts`: the Rejseplanen client, one function per service (`journeyPos`, `himsearch`, `multiDepartureBoard`, `multiArrivalBoard`, `journeyDetail`), every attempt counted before it is sent.
- `join.ts` joins a journey to its trip, taking the corrections opened trips' details made; `build.ts` builds the snapshot's trips with the domain rules from the answer and each trip's history between runs; `snapshot.ts` is the snapshot's schema, whose types the browser imports.
- `health.ts`: the API's health (ok, empty, error, spent) and when it began.
- `disruptions.ts`: the disruption list between fetches, each message as received with its fields' kind, the modes its products concern and its validity as moments; `src/domain/disruption.ts` reads the kind its card names and whether it is active or Later.
- `report.ts`: what each run reports, in its log line and the snapshot's status section, and the CPU clock it measures itself by.
- `budget.ts`: the pacing rule: the month's line, the gap and the level, which sets the poll interval, the disruption fetches and whether on-demand calls are allowed.
- `aircraft/`: the aircraft source (`docs/aircraft.md`, ADR 0014), apart from the tracker and with its own runtime: `answers.ts`, the readsb answer's schema adsb.lol and adsb.fi share, and its contract fixture in `fixtures/`; `source.ts`, `MYLDER_AIRCRAFT_SOURCE` and how a recording keeps the feed's calls (`RECORDED_AIRCRAFT`); `build.ts`, the aircraft an answer keeps; `aircraft.ts`, the `Aircraft` service, one call every 10 s shared by the requests that come meanwhile; `snapshot.ts`, the aircraft snapshot's schema, whose types the browser imports from `index.ts`; `runtime.ts`, its runtime from the environment; `routes.ts`, the route's answer (`aircraftResponse`).
- `siri-et/`: the SIRI-ET reader (spec #146, ADR 0019), apart from any runtime so the listener and the tracker can both run it: `siri.ts` reads one message body's journeys in one pass over its tags; `reader.ts` merges each journey's calls across messages and gives the update table at a moment, dropping finished journeys and holding to its caps; `table.ts` is the table's versioned schema, the listener's and the tracker's contract; `recording.ts` reads a recorded folder's messages and the box's stops from its timetable. Its tests replay `fixtures/sample.jsonl.gz`, eight journeys of `recordings/siri-et/`.
- `remember.ts`: a value built once and forgotten when its build fails, such as each runtime, whose layers are built with it.
- `store.ts`: the store's four operations, in memory until the hosted Redis (#56); `caching.ts`: the CDN header and an answer's cache policy (the tracker's is `TRACKER_CACHING`, the aircraft's `AIRCRAFT_CACHING`); `cdn-answer.ts`: the answers any feed's routes build with it, knowing no feed (`cdnAnswer`, and its 404 and 503); `routes.ts`: the tracker's route answers, built with `cdnAnswer`, and the timetable files'.
